# 把散落一地的本地 AI 服务，装进一张网页卡片 —— AI 工作台开发手记

> 项目地址：https://github.com/roseion/ai-workbench
> 技术栈：Node.js + Express + 零构建原生前端，后端唯一依赖是 express，前后端合计不到三千行。

## 缘起：每天开工前的"寻宝仪式"

作为一个折腾本地 AI 的个人开发者，我的机器上攒了一堆服务：

- 一个 bat 一键拉起 SillyTavern（8000）+ AI 写作工坊（8090）+ Ollama（11434）；
- 一个写小说的生成器项目，藏在另一个目录，靠它自己的 `启动.bat`；
- 一个跑在 Docker Compose 里的 API 网关，日常操作是 `docker ps`、`docker logs -f`、`docker compose pull && up -d`；
- 一个 IM 类 Agent 项目，双击 bat 后去开 `127.0.0.1:27182`；
- 甚至还有一个纯静态的中国象棋页面，直接双击 HTML 就能玩。

每个项目的启动方式、端口、目录、停止姿势都不一样。开工前我得在资源管理器里逐个翻文件夹，停止时更麻烦——bat 用 `start` 拉起的服务，关掉命令行窗口后进程还活着，得开任务管理器按名字猜着杀。

麻烦到一定程度，解决方案就自己浮出来了：**给它们做一个网页"中控台"，每个服务一张卡片，启动、停止、重启、打开，一个页面搞定。**

需求很朴素，我顺手写在了 `项目需求.md` 里，其中有一条当时看起来有点超前：

> 能手动添加新的项目，也允许其他 AI 同事在建立别的项目后，直接把项目添加到工作台。

这条需求后来被证明是整个项目里最有意思的设计，后面细说。

## 开发思路：三个关键设计

动手之前想清楚了几件事。本地工具最容易做成"一次性脚本"，我想让它至少满足三条：**轻量到随时能改、诚实到不出假状态、开放到别的程序能接进来。**

### 1. 启动器是一个可插拔的抽象

我的服务有三种形态：bat 拉起的、Docker Compose 跑的、纯静态页面。它们启动/停止/查状态的方式完全不同，但对外表现应该一样——都是一张能点按钮的卡片。

于是有了 `server/launchers/` 下的启动器抽象：每个启动器实现统一接口，并用一个 `capabilities` 对象声明自己会什么：

```js
// server/launchers/static.js —— 最简单的一个，全文 13 行
module.exports = {
  capabilities: { canStart: false, canStop: false, canRestart: false, canOpen: true },
  async getStatus() { return { status: 'idle' }; },
  openUrls: require('./base').openUrls,
};
```

这个设计换来了一个我很喜欢的效果：**前端按钮按能力声明自动渲染**。static 类型的卡片上压根不会出现"停止"按钮，REST 层的校验也按注册表自动生效。以后想加 systemd、PM2 甚至远程 SSH 启动器，就是"一个文件 + 一行注册"的事。

### 2. 状态判定：相信端口，不信猜测

"这个服务到底在不在跑？"是这类工具最容易撒谎的地方。进程在 ≠ 服务可用（可能还在启动中），窗口关了 ≠ 进程没了。

最终的优先级链是：**端口探测 > 跟踪中的 PID > 用户手动标记 > 启动宽限期 > unknown/stopped**。端口是最诚实的信号——服务声明了自己用哪个端口，端口能连通就是 `running`。而对于没有端口、又不是工作台自己拉起的进程，状态直接给 `unknown`，不装懂。

### 3. 数据与 API：文件 + REST + 自描述 Schema

数据就是 `data/projects.json`，原子读写（先写临时文件再改名），没有数据库。API 是朴素的 REST，但多做了一步：`GET /api/v1/schema/project` 返回一份自描述的 JSON Schema，字段规范、示例、默认值全在里面。

这就是"AI 同事接入"的落点。我的大部分项目本来就是我跟 AI 结对写出来的——AI 建完新项目后，不需要我手动去工作台补卡片，一个 HTTP 请求就能注册进来：

```bash
curl -X POST "http://127.0.0.1:8787/api/v1/projects" -H "Content-Type: application/json" -d '{
  "name": "我的新 RAG 服务", "type": "script",
  "path": "D:/ai/my-rag/启动.bat", "ports": [8901], "urls": ["http://127.0.0.1:8901"]
}'
```

工作流从此闭环：**AI 写项目 → AI 注册项目 → 我在一张卡片上点"启动"。** 安全上做了对应收缩：默认只监听 `127.0.0.1`，写操作可选 `WORKBENCH_TOKEN` 鉴权，入参校验里专门做了防命令注入。

## 踩坑实录

### 坑一：双击一切正常，经工作台启动就报 9009

第一个靶子是 AgentIM。它的 bat 双击运行好好的，从工作台启动却直接失败，退出码 9009（cmd 的"命令找不到"），报错信息里还夹着 bat 中间行的残段——像是整个脚本被"撕碎了"随机执行。

排查下来是一个相当冷门的 cmd 行为：**这个 bat 里有全角标点的中文 `REM` 注释，而工作台启动时把它的输出重定向到了管道。cmd 在"输出被重定向"的场景下解析批处理会错位，注释行之后的行被切碎、碎片当成命令执行。** 双击运行时输出走控制台，不触发这个缺陷；预置 `chcp 65001` 也没用。

两层解决：

1. 治本：把这类注释行从 bat 里删掉（顺手发现这个文件行尾还是 LF，**bat 必须保持 CRLF**，否则一样解析错位——这是编辑器写文件时容易踩的另一个坑）；
2. 治标且通用：给启动器加了 `options.console` 选项，用 `start` 在**新控制台窗口**里运行，完全等同双击效果。代价是工作台捕获不到它的输出，所以做成可选项而不是默认值。

### 坑二：一次真实事故——taskkill 误杀了无辜的 Docker 容器

为了停止"工作台自己启动的进程"，初版逻辑很直接：记住 spawn 返回的 PID，停止时 `taskkill /PID x /T /F`。直到某天我停一个项目，旁边跑着的 freellmapi 容器莫名其妙死了（Exit 137），第二次复现时连工作台自己都跟着退出了。

根因是 Windows 的 **PID 复用**：被跟踪的子进程退出后，它的 PID 可能被系统分配给完全无关的进程。此时拿着旧 PID 去 `taskkill /T /F`，等于对随机路人执行连坐。

修复原则变成了一句话：**杀任何跟踪中的 PID 之前，先核对它的"命令行指纹"**：

```js
// 核对 PID 身份：Windows 会复用 PID，结束跟踪进程前先确认命令行指纹匹配，
// 避免把复用了旧 PID 的无辜进程（及其整棵进程树）误杀
async function pidMatchesCommandline(pid, substr) {
  // Get-CimInstance Win32_Process -Filter "ProcessId=x" 后比对 CommandLine
}
```

指纹取自启动时记录的 bat 路径/命令，比对不上的一律放过。这三行防御后来再没让事故重演——代价只是停止时多一次百来毫秒的 WMI 查询，值。

### 坑三：bat 用 `start` 拉起服务后，进程"失联"了

比 PID 复用更普遍的问题是：现实世界的 bat 十有八九是这种结构——

```bat
@echo off
start "服务" node server.js   &  rem 拉起孙进程
exit                          &  rem 脚本自己退出，进程树断裂
```

`start` 拉起的孙进程和脚本已经没有进程树关系，脚本一退出，工作台手里的 PID 就成了废纸。没有银弹，只能按可靠性递减做三层兜底：

1. **本次启动跟踪的 PID**（先过指纹核对）；
2. **端口反查**：对卡片上声明的端口跑 `netstat -ano` 找 LISTENING 的 PID；
3. **命令行匹配**：`options.processMatch` 配一个足够独特的关键字（比如 `daemon.mjs`），用 WMI 按命令行搜。

三层全落空时，如实返回"进程未跟踪"，绝不猜着杀。这个策略连同 PID 指纹核对，一起写进了 `server/probe.js` 和启动器里。

### 坑四：小坑合集（附带教训）

- **Git Bash 的 curl 发中文 JSON 会 GBK 乱码**，一旦写进数据文件就永久污染。后来发中文 payload 一律用临时 Node 脚本。
- **`node --test test/` 会把 fixtures 目录当测试用例**然后挂起，必须用 glob 形式 `node --test "test/*.test.js"`。
- **HTML5 拖拽必须真的写 `draggable="true"`**。听起来像废话，但当时的自动化测试用合成事件模拟拖拽——合成事件会绕过原生拖拽的启动检查，测试全绿、真人拖不动。教训：**合成事件测不出平台集成层的问题**，这类交互最终得靠真手验。

## 彩蛋：工作台如何管理它自己

做到一半意识到一个有趣的递归问题：工作台自己也是一个本地服务，凭什么它不在卡片里？于是它把自己注册成了第一张卡片。麻烦也随之而来：

**自己停自己**：如果在 HTTP 请求处理里直接 `process.exit(0)`，响应还没发出去就断了。所以 `stop` 里认出自己的 PID 时先记一笔，等响应发出后再延迟 600ms 退出。

**自己重启自己**：新实例必须由别人拉起。方案是一个分离的引导进程：

```js
spawn('cmd.exe', ['/d', '/c', 'ping', '-n', '3', '127.0.0.1', '>nul', '&', 'start', '', bat],
      { detached: true, stdio: 'ignore' }).unref();
```

两个细节值得记：用 `ping -n 3` 而不是 `timeout 2` 做延时，因为 **timeout 在 stdin 被重定向时会立即报错退出**；引导命令不落盘成 bat 临时文件，因为批处理文件会被 GBK 代码页误读中文路径，而参数数组经 `CreateProcessW` 以 UTF-16 传递，天然 Unicode 安全。

点"重启"，页面短暂断开两秒，然后自己回来——这个功能没什么实用价值，但很有"完成感"。

## 测试：为真实世界写一个夹具

单元测试不难写，难的是把坑三那种真实场景固化下来。`test/fixtures/fixture-start.bat` 就是照着现实世界的坏 bat 造的（节选）：

```bat
@echo off
cd /d %~dp0
start "wb-fixture" /min node fixture-server.js
exit
```

`start` 拉起子进程后立刻退出——和工作台要管的那些服务一模一样。集成测试跑完整闭环：创建 → 启动 → 端口探测确认存活 → 停止（验证端口反查真的找到了孙进程并结束它）→ 删除。现在共 23 个用例，`npm test` 跑完不到半分钟，之后每次改停止策略心里都有底。

## 写在最后

回顾这个项目，最大的收获有两个。

一是**对 Windows 进程管理存了敬畏**。"杀掉一个进程"在 Linux 上是 `kill` 一个词，在 Windows 上是 PID 复用、进程树断裂、控制台重定向解析差异、GBK 代码页四座大山。负责任地杀进程，比启动进程难得多。

二是**"让 AI 同事接入"这个决定回报巨大**。当初只是需求文档里顺手写的一行，做完之后它改变了我开新项目的姿势：AI 负责建项目并注册，我负责在一张卡片上点按钮。工具从一开始就为"人机协作"留了接口，这是纯手动时代不会有的设计。

项目已经开源：**https://github.com/roseion/ai-workbench**，`git clone` + `npm install` + `npm start` 三步跑起来，欢迎 star / 提 issue。已知限制（比如工作台启动前手动拉起的无端口进程无法识别）都如实写在 README 里——一个诚实的工具，从 README 开始。
